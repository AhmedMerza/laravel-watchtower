# Changelog

All notable changes to `laravel-watchtower` will be documented in this file.

## [Unreleased]

## [0.2.0] - 2026-09-17

### Security

- **Sync requests were signed but nothing verified the signature.** Satellites computed an HMAC and sent it; the package shipped no verification code and no master-side routes. The README instead asked adopters to hand-write two unauthenticated closures at `/guard/api/blacklist` and `/guard/api/block`, so anyone who could reach the master could block any IP — and have it propagate to every satellite on the next sync — or read the full blocklist. Watchtower now ships the master side: `GET /watchtower/sync/blocks` and `POST /watchtower/sync/block`, registered automatically when `WATCHTOWER_SYNC_SECRET` is set, outside the `web` group, behind a new `VerifySyncSignature` middleware that recomputes the signature with `hash_equals` and rejects timestamps outside a configurable window. ([#12](https://github.com/AhmedMerza/laravel-watchtower/issues/12))

### Changed

- **BREAKING: package renamed — `ahmedmerza/logscope-guard` → `ahmedmerza/watchtower`.** Reflects the strategic pivot away from "LogScope addon" toward "standalone Laravel app-edge blocker, with optional LogScope integration."
- **BREAKING: namespace renamed — `LogScopeGuard\` → `Watchtower\`.** All `use LogScopeGuard\…` imports must be updated.
- **BREAKING: service provider renamed — `LogScopeGuardServiceProvider` → `WatchtowerServiceProvider`.**
- **BREAKING: config file renamed — `config/logscope-guard.php` → `config/watchtower.php`.** Re-run `php artisan vendor:publish --tag="watchtower-config" --force` if you've published a customized version.
- **BREAKING: all env vars renamed — `GUARD_*` → `WATCHTOWER_*`.** Backward-compat aliases are in place until v1.0 — `WATCHTOWER_*` takes precedence, but if unset, the old `GUARD_*` values are still consulted. Scheduled to be removed in v1.0. The one exception is `GUARD_REDIS_CONNECTION`, which has no replacement (see the cache abstraction under Added).
- **BREAKING: artisan commands renamed — `guard:install` → `watchtower:install`, `guard:sync` → `watchtower:sync`.** Update the `guard:sync` schedule entry in your app.
- **BREAKING: cache key renamed — `logscope_guard:blacklist` → `watchtower:blacklist`,** which is now the prefix for per-IP entries rather than a single hash (see the cache abstraction under Added). On first boot under the new name, the old Redis key is ignored and the cache is rebuilt from the DB. No data loss; just a brief warm-up window. Nothing deletes the old key, so remove it by hand if you want the memory back.
- **BREAKING: HTTP routes moved — `/logscope/guard/*` → `/logscope/watchtower/*` (LogScope mode) or `/watchtower/*` (standalone mode).** Update any external callers.
- **BREAKING: sync headers renamed — `X-Guard-Signature` → `X-Watchtower-Signature`, `X-Guard-Timestamp` → `X-Watchtower-Timestamp`.** The sync paths moved too (below), so **master and satellites must be on the same version** — mixing pre/post-rename versions across envs will fail signature verification.
- **BREAKING (LogScope integration): the Block IP button needs LogScope 1.6.1 or later** (was 1.5.2). LogScope 1.5.2 through 1.6.0 include the pre-rename `logscope-guard::partials.ip-actions`, a namespace this package no longer registers, so on those versions the button doesn't render. `composer.json`'s `suggest` and the README say `>=1.6.1`, and the `prefer-lowest` CI job tests against a version where the integration exists.
- **BREAKING (sync wire protocol): the sync paths moved from `/guard/api/blacklist` and `/guard/api/block` to `/watchtower/sync/blocks` and `/watchtower/sync/block`,** off the management API and away from `WATCHTOWER_ROUTE_PREFIX` — the satellite signs the path it calls, so it can't depend on the master's prefix config. Master and satellites must be upgraded together. The signed string is unchanged in shape (`timestamp + METHOD + path + rawBody`) and now has a single implementation, `Watchtower\Support\SyncSignature`, used by both the clients and the middleware.
- **`PushBlockToMaster` no longer re-pushes a block that arrived by sync,** and the master ignores an incoming push for an IP already blocked locally by hand or by auto-block. Without both, a master whose own `WATCHTOWER_MASTER_URL` points at itself — the documented setup — would push every incoming block straight back to itself in a loop.
- **`watchtower:sync` now fails with a clear message when `WATCHTOWER_SYNC_SECRET` is unset,** and `PushBlockToMaster` logs a warning instead of sending a request the master will reject.
- **A push the master rejects now fails loudly.** The job asks for JSON and no longer follows redirects, so a validation failure comes back as a 422 and retries instead of being answered with a 302 to the master's home page whose 2xx read as success — which lost the block silently. An over-long `reason` is clipped to the 500 characters the master accepts before sending, rather than failing validation on arrival.
- **The sync secret is read identically everywhere** via `SyncSignature::secret()` — trimmed, and compared against `''` rather than tested for truthiness. Previously nothing trimmed it, so a trailing space from `.env` quoting became part of the HMAC key on one side of the fleet only.
- **BREAKING: `illuminate/*` is bounded to `^12.0|^13.0`, and CI tests both.** The constraint was an open `>=10.0`, so composer installed the package on Laravel 13 — and on any future major — even though the suite had never run there; the matrix varied PHP and `prefer-lowest`/`prefer-stable` but never the framework, so it couldn't have caught a break either. Each test job now pins a Laravel major and lets composer pick the `orchestra/testbench` that goes with it (`^10.0|^11.0`), so the matrix can't drift from what `composer.json` declares, and each end of the range gets a `prefer-lowest` run. Static analysis runs on Laravel 12 and 13 rather than on whichever major composer resolves as newest, since PHPStan's verdict on this code differs between them. The TrustProxies lookup in the service provider also dropped its `is_string()` guard, redundant in front of `is_a()` and read as always-true by PHPStan under Laravel 13's narrower `getGlobalMiddleware()` PHPDoc. ([#15](https://github.com/AhmedMerza/laravel-watchtower/issues/15))
- **Laravel 11 is no longer supported, because it can no longer be installed.** Laravel 11 is past security support, and the advisories that close `PKSA-mdq4-51ck-6kdq`, `PKSA-3r5d-mb8f-1qw9` and `PKSA-m5cs-t1y6-qpcs` were only ever fixed in 12.60/12.61.1 — no patched 11.x exists or will. Composer 2.10 refuses a release with an open advisory by default, so every stable 11.x is unreachable: an app on Laravel 11 cannot resolve the framework at all, and this package's own CI was quietly falling through to the unreleased `11.x-dev` branch on both of its Laravel 11 jobs. Supporting a version nobody can install, in a package whose job is blocking traffic, isn't a support claim worth making.
- **`minimum-stability` and `prefer-stable` are gone from `composer.json`,** which restores composer's default of `stable`. `dev` was what let the advisory-blocked resolutions above fall through to branch builds — `guzzle 7.8.x-dev` and `psr7 1.9.x-dev` were being installed on every `prefer-lowest` job for the same reason. Every CI job now installs released versions only.
- **BREAKING (subclassers only): `BlacklistCache::rebuild()` returns `bool` instead of `void`.** It reports whether the DB read succeeded, so `warmOnBoot()` can stand down when it didn't. PHP does not permit a `void` override of a `bool` method, so any subclass overriding `rebuild(): void` must update its signature. Callers that ignore the return value are unaffected.
- **Laravel 10 was never actually supported,** despite the old `>=10.0` constraint: the service provider uses the `Illuminate\Support\Facades\Schedule` facade, which only exists from Laravel 11. Laravel 10 is also past its security-support window. Surfaced by a new `prefer-lowest` CI job.
- **A blocked request now gets a bare response instead of going through `abort()`.** The middleware returns `block_response.message` with `block_response.status` directly, so the app's exception handler never sees it: blocked visitors get the message as plain text rather than the app's error page (a custom `errors/403` view, or Laravel's default), and clients that expect JSON no longer get a JSON body. `block_response.redirect` works as before.

### Added

- **Cache abstraction — Redis is no longer a hard dependency.** `BlacklistCache` now uses `Cache::store(config('watchtower.cache.store'))` instead of direct Redis facade calls. Any cache driver Laravel supports works: redis, memcached, file, database, array, dynamodb. New env var `WATCHTOWER_CACHE_STORE` (default falls back to your app's `cache.default`). Internally the cache uses per-IP keys (`{prefix}:ip:{ip}`) plus a sidecar index (`{prefix}:_index`) so `rebuild()` can clear stale entries on any driver — no `Cache::tags()` requirement (file/database stores don't support tagging). `composer.json` `require` swaps `illuminate/redis` → `illuminate/cache`. The legacy `cache.connection` key (`GUARD_REDIS_CONNECTION`) is ignored by the new code and has been removed from the config schema ([#32](https://github.com/AhmedMerza/laravel-watchtower/issues/32)); users wanting a non-default Redis connection should now configure a custom cache store in `config/cache.php` and point `WATCHTOWER_CACHE_STORE` at it. Performance: request-time is unchanged (one cache `get`); rebuilds do N+1 writes vs. the previous single HMSET, but rebuilds are rare (only on block/unblock/sync).
- **Auto-block warn-only mode** — new `watchtower.auto_block.mode` config (`block` | `warn` | `disabled`, default `block`) plus optional per-rule `mode` override. In `warn` mode, the engine matches rules and emits a structured `would_have_blocked: true` log entry on the configured `log_channel`, but does NOT actually block — operators can validate a rule against real traffic before flipping it to `block`. `disabled` skips a rule entirely (per-rule kill switch). New env var: `WATCHTOWER_AUTO_BLOCK_MODE`. Backward-compatible: configs that don't set a mode get the prior `block` behaviour.
- **Standalone routing config block (`watchtower.routes.*`).** Previously the package only knew how to mount routes under LogScope's prefix — when LogScope was absent, it still read `config('logscope.routes.prefix', 'logscope')` (a leak from a foreign config namespace, working only by virtue of the default). The standalone branch now reads `watchtower.routes.prefix` (default `'watchtower'`), `watchtower.routes.domain`, and `watchtower.routes.middleware` from the package's own config. New `WATCHTOWER_ROUTES_ENABLED` env flag lets users disable the management routes entirely.
- **`watchtower:install` detects LogScope and prints branch-specific next-steps.** Standalone users get a prominent warning that the management routes have no built-in auth until v1.0.
- **`watchtower:cleanup`** deletes expired temporary blocks from the database and rebuilds the cache. Watchtower schedules it daily; set `WATCHTOWER_CLEANUP_ENABLED=false` to run or schedule it yourself.
- **`watchtower.log_channel`** (`WATCHTOWER_LOG_CHANNEL`, default `stack`) — the channel Watchtower writes its own warnings and errors to. 0.1.0 hard-coded `stack`. Messages are now prefixed `Watchtower:` instead of `LogScope Guard:`, so update any alert that matches the old prefix.
- **`watchtower.sync.timestamp_tolerance`** (`WATCHTOWER_SYNC_TOLERANCE`, default 300 seconds) — how far a signed request's timestamp may sit from the master's clock. Bounds the window in which a captured request can be replayed.

### Documentation

- The sync section now says that the routes come up on **any** environment with a secret, satellites included, since registration is gated on the secret alone and satellites need it to sign ([#36](https://github.com/AhmedMerza/laravel-watchtower/issues/36) tracks separating the two capabilities). It also warns to keep satellite egress IPs in `WATCHTOWER_NEVER_BLOCK_IPS` on the master: the blocking middleware is global, so a blocked satellite stops syncing in both directions and `watchtower:sync` reports only `HTTP 403`.

### Fixed

- **Blocks were ignored behind a load balancer or reverse proxy.** The blocking middleware was prepended to the global stack, ahead of `TrustProxies`, so `$request->ip()` returned the proxy's address and never matched a blocked client IP. It is now inserted directly after `TrustProxies` (or an app subclass of it), still ahead of sessions, auth and routing. If `TrustProxies` isn't in the global stack, it still goes first. ([#14](https://github.com/AhmedMerza/laravel-watchtower/issues/14))
- **A cache outage no longer makes every request return 500.** If the blocklist lookup throws (Redis down, a mistyped `WATCHTOWER_CACHE_STORE`), the request is let through unchecked and the failure is logged at `error` on `watchtower.log_channel`, at most once a minute across all workers. ([#13](https://github.com/AhmedMerza/laravel-watchtower/issues/13))
- **The boot-time cache warm-up no longer fails every request, or floods the log, during an outage.** `warmOnBoot()` runs on every request. A cache outage made it throw, so every request returned 500 before the blocking middleware even ran; a DB outage made it write its own `warning` each time. A failed warm-up is now logged and stands down for a minute, which also drops the repeated doomed round-trip to the dead backend. The throttle is not atomic: requests already in flight at the onset of an outage can each log once before the window closes. ([#13](https://github.com/AhmedMerza/laravel-watchtower/issues/13))
- **An empty blocklist no longer costs a DB query on every request.** `rebuild()` left the cache key unset when no IPs were blocked, but `warmOnBoot()` reads a missing key as "needs warming" — so a site with an empty blocklist (the default state of a fresh install, or any site whose blocks have all expired) re-ran `BlacklistedIp::active()->get()` on every single request, forever. `rebuild()` now writes an empty index instead.
- **Watchtower now warns when `TrustProxies` isn't in the global middleware stack.** In that case blocking runs first and sees the direct peer address, which behind a proxy is the proxy's IP — the same silent failure as [#14](https://github.com/AhmedMerza/laravel-watchtower/issues/14). The warning goes to `watchtower.log_channel`, throttled.
- **A failed cache rebuild no longer lifts every block.** `rebuild()` deleted the cached blocklist before reading the database, so when the read failed, the cache stayed empty and every block was lifted until a later rebuild succeeded, even though the logged warning said the existing data was kept. It now reads the database first and leaves the cache untouched when that fails.
- **`watchtower:sync` no longer reports success when the cache rebuild failed.** `rebuild()` catches its own DB-read failure, but the command carried on, reported the sync and exited 0. Cron recorded a green run while the cached blocklist was wrong, and the only signal was a warning on a log channel nothing was watching. It now says what actually happened and exits non-zero, so a scheduler surfaces it. The new `watchtower:cleanup` does the same. ([#33](https://github.com/AhmedMerza/laravel-watchtower/issues/33))
- **A block or unblock now takes effect even when the cache rebuild after it fails.** The blocking middleware reads only the cache, and `BlacklistService` ignored a failed rebuild — so when the DB read timed out right after the write (most likely on a large blocklist under load, exactly when auto-block is busiest), `block()` saved the row, fired `IpBlocked`, pushed to the master and reported success while the IP went unblocked, and `unblock()` returned `true` while the IP stayed blocked, both until the next successful rebuild or up to 24h. This affected auto-block, the API and LogScope's Block IP button, and a master accepting a pushed block. `block()` now writes that IP's cache entry directly when the rebuild fails, and `unblock()` always forgets the IP's own entry. `watchtower:sync`, which writes rows without going through `block()`, had the same gap for every IP it had just pulled from master — loud since #33, but unenforced until a later run's rebuild succeeded. It now writes those entries directly too, and still exits non-zero. ([#42](https://github.com/AhmedMerza/laravel-watchtower/issues/42))
- **A database or cache failure while blocking is no longer reported as "IP is whitelisted".** `block()` refused a never-block IP with a plain `RuntimeException`, and every caller caught any `RuntimeException` as that refusal — but `QueryException` and phpredis's `RedisException` are `RuntimeException`s too. So a failed write was logged by auto-block as a whitelisted skip at `debug`, where production rarely looks; the API and LogScope's Block IP button answered 422 with the raw exception message, which for a `QueryException` includes the SQL and its bindings. The refusal is now `Watchtower\Exceptions\NeverBlockException`, which still extends `RuntimeException`, so existing `catch (\RuntimeException)` code keeps working, and the callers catch only that. A real failure now surfaces: auto-block's scheduled run fails and reports it, and both endpoints return a 500. ([#44](https://github.com/AhmedMerza/laravel-watchtower/issues/44))

### Upgrading from `logscope-guard` 0.1.0

- **There is no transitional `ahmedmerza/logscope-guard` package.** It has been removed from Packagist. To upgrade, `composer remove ahmedmerza/logscope-guard`, `composer require ahmedmerza/watchtower`, then work through the BREAKING entries under Changed.
