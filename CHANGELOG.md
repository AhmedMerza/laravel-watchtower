# Changelog

All notable changes to `laravel-watchtower` will be documented in this file.

## [Unreleased]

### Changed

- **A scanner probe now costs 6 cache round trips instead of ~11, by removing redundant ones rather than batching them.** The detector path is paced by whoever is probing it, so every avoidable round trip on it is an attacker's lever: at ~1,000 probes a day the old path spent ~10,000 round trips that bought nothing, and a burst day multiplied that. Three separate redundancies, none of which changes behaviour ([#69](https://github.com/AhmedMerza/laravel-watchtower/issues/69)):

  **The blocklist was checked twice per request.** `BlockedIpMiddleware` asks "is this address blocked" — two reads, the ranges key and the per-IP key — and then `AutoBlockService::detect()` asked again for the same address moments later in the same request. It now reads the verdict the middleware already paid for, stashed on the request beside the client IP it already stashed there. The second answer could only differ if a block landed in the microseconds between them. The stash is only written for a verdict actually read from the cache, so the paths that return without one — Watchtower disabled, no resolvable address, `never_block`, or a cache read that threw and failed open — leave it absent and a reader looks it up itself. The saving never costs correctness.

  **The hit counter wrote a `:timer` key nothing ever read.** `HitWindow` used Laravel's `RateLimiter`, which keeps that sidecar so `availableIn()` can report how long a caller must wait. Watchtower only ever calls `hit()` and the clear, never asks the wait, and paid a write for the key on every hit plus a delete on every clear. `RateLimiter::increment()` is now inlined without it, keeping the part that matters — the repair for a counter that expires mid-hit and comes back on some stores with no TTL at all, which would never decay and pin an address at its threshold forever. Existing `:timer` keys are orphaned by the upgrade and expire on their own within the window; nothing reads them in the meantime.

  **The user set was deleted even when it was never written.** Most detector traffic is anonymous and never opens one, so the delete spent a round trip on an absent key. `HitWindow::users()` and `forget()` are replaced by a single `close()`, which reports the users it is dropping and skips the delete when there were none. Folding them also removes a foot-gun the old pair carried: closing drops the set, so reading it *after* the clear returned nobody — silently, since "no users" is an ordinary answer — and the correct order was a comment to obey rather than something the API enforced. `users()` remains as a read-only accessor. A caller of `HitWindow::forget()` — an internal support class, not part of the documented surface — should now call `close()`.

  **A test counts the operations, so this can't quietly rot.** Cache reads fire no events and the `add()`/`increment()` pair fires nothing at all, so the assertion runs against a cache store that records every operation underneath the Repository. It pins the exact sequence rather than a total, so a change that reintroduces a round trip shows up as a readable diff. Each of the three savings was confirmed by reverting it and watching the matching test fail.

  **Redis pipelining, which the issue proposed, is deliberately not part of this.** After the removals it would save 2 of the remaining 6, and the remaining pairs are mostly *dependent* anyway — the per-IP blocklist read needs the `ipv6_prefix` from the ranges read, and the TTL repair needs the increment's result. Against that: the package has no Redis in CI and no `predis`/`phpredis` requirement, so a `RedisStore` fast path would be the one code path never exercised by the test suite; `PhpRedisClusterConnection` inherits a `pipeline()` that calls a method `\RedisCluster` does not have, so on a cluster it is a fatal rather than a fallback; and `AutoBlockService::record()` fails open by design, so that fatal would be swallowed and real-time detection would simply stop, one log line per failure window. A security package that quietly stops detecting is a worse outcome than one that is two round trips slower.

## [0.6.0] - 2026-09-22

### Added

- **`watchtower:simulate` backtests the auto-block rules against the log history you already have, so you can see what a rule would have done last week instead of arming it and waiting.** `warn` mode is the honest way to try a rule out and it costs days — set it, wait, read logs. Watchtower can skip the waiting because LogScope kept the history the rule would have read; no other Laravel firewall package can do this for the plain reason that none of them has the data. `php artisan watchtower:simulate --days=7` reports, per rule, which addresses would have been blocked, when, and how many times, how many distinct signed-in users each address showed, and — the number that should actually stop you — how many requests came from that address carrying a signed-in user and never matched the rule at all. Those are people doing nothing wrong who would have lost access anyway. It also flags what the shared-IP guard would have done to each address, computed against the window the live guard would really have read rather than the period as a whole, so it doesn't predict downgrades that wouldn't happen. `--rule=N` narrows to one rule and `--json` is for CI. It reports every configured rule regardless of `auto_block.enabled` or a rule's `mode`, because deciding those is the reason to run it. ([#24](https://github.com/AhmedMerza/laravel-watchtower/issues/24))

  **It writes nothing, and the database enforces that rather than a reviewer's attention** — the test installs `BEFORE INSERT/UPDATE/DELETE` triggers that abort on `blacklisted_ips`, `ip_offences` and the log table, then runs the command with a rule set to `block`. A row count taken afterwards would have missed a write that changed nothing or one rolled back inside a transaction; a trigger fails on the attempt. `RuleSimulator` is a separate class from `AutoBlockService` for the same reason: there is no path from a backtest into `BlacklistService` for a future change to forget.

  **It knows what the engine knows, including the awkward parts.** A rule whose `scope` isn't declared in `watchtower.scopes` is reported as skipped rather than simulated, because `AutoBlockService::run()` skips it outright — a report of what such a rule "would have caught" describes a rule that never runs. Addresses covered by `never_block` or `never_auto_block` are listed separately instead of counted as would-be blocks, since `BlacklistService::block()` refuses them whatever a rule says, and those are precisely the addresses (your own office, a partner) an operator most needs a straight answer about. And on a **scoped** rule the shared-IP guard does not hold a block back — `blockOrReport()` converts it into a real block narrowed to that scope, which is the entire reason scopes exist — so the report says "scoped", not "warning". The allow-list predicate now lives in one place, `Support\NeverBlockList`, which `BlacklistService` also uses, so a backtest and a real block cannot reach different conclusions about who is protected.

  **The replay reads from before the period it reports on.** A rule's window is wall-clock and knows nothing about `--days`: two matching rows just before the cutoff and a third just after is a genuine 3-in-5-minutes crossing, and the engine would have blocked it. Bounding the read at the cutoff dropped the first two and missed the block — under-reporting, the one direction this must never err in. Rows are now read from one window earlier, and only crossings inside the requested period are reported.

  **Three inexactnesses, all documented in the README and all erring towards over-reporting.** The engine evaluates on a one-minute scheduler tick while the replay notices a crossing at the row that caused it, up to a minute earlier. Escalating durations are not modelled, so every simulated block lasts `block_duration_minutes`. And rules are replayed independently while the live engine skips an address another rule has already blocked, so two overlapping rules can both claim the same address.

  **Memory is bounded; query cost depends on your data.** Each address is replayed through a fixed-size ring buffer holding at most `count` timestamps, so one that logged a million rows costs the same as one that logged fifty. The keyset paging orders on `(occurred_at, id)` rather than `occurred_at` alone, because log rows share a timestamp constantly — a burst inside one second is the entire subject of this command — and a keyset on a non-unique column silently skips the rest of that second at every page boundary. Query cost is the honest caveat: the narrowing pass admits any address with `count` matching rows *anywhere in the period*, a much weaker filter than `count` inside one window, so busy traffic admits addresses that never trip the rule and each is streamed individually. LogScope has no `(ip_address, occurred_at)` index, so those reads have no ideal plan; the README says which index to add for a large table, and [#75](https://github.com/AhmedMerza/laravel-watchtower/issues/75) tracks whether it pays for itself.

### Changed

- **BREAKING: `GET /api/blocks` is paginated, and takes the management page's filters.** It returned every active block in one array — fine for the LogScope panel, which asks about one address, and not something a client can page through. `data` is now one page of rows (25 by default, `?per_page=` up to 100) inside Laravel's standard paginator body, with `total`, `last_page` and the page URLs beside it. **Anything reading `data` as the complete list now sees at most one page**; read `total` and follow `next_page_url` for the rest. `?source=manual|auto|sync` and `?state=active|expired|all` narrow the list, and `?state=active` remains the default, so an existing caller's *first* page holds the same rows it used to see first. The filters go through the same `BlacklistedIp::scopeFilter()` and the same normalisation the management page uses — now `Support\BlockFilters`, rather than a private method on one controller — so exposing them here didn't create the second copy that issue [#38](https://github.com/AhmedMerza/laravel-watchtower/issues/38) is about. An unrecognised filter value lists active blocks instead of returning a 422, matching the page. ([#64](https://github.com/AhmedMerza/laravel-watchtower/issues/64))

  **Token authentication for non-browser clients is deliberately still not built.** The other half of #64 was an auth story for a mobile or CLI caller, and it stays open on purpose: which user a token resolves to, what `blocked_by` should record for one, and whether a token may create blocks or only read them are decisions that go wrong when they're made against an imagined consumer. No client exists yet, so the management routes keep `watchtower.routes.middleware` plus the `viewWatchtower` Gate, and the README now says so where someone would look for it. A real client is the trigger to design it.

### Fixed

- **Both block lists now break a `created_at` tie on the row id, so paging can't drop or repeat a block.** `created_at` is a second-resolution timestamp and a sync pull or an auto-block burst writes a batch of rows inside one second, so ties are ordinary rather than exotic. Ordering on it alone leaves the tied rows free to come back in a different order for each page's query — on MySQL and Postgres, which guarantee no order among equal sort keys — so a row could appear on two pages or on none, and a client enumerating the list by following `next_page_url` would silently miss blocks. The id is a ULID, so it is unique and already time-ordered: as a tiebreaker it settles ties without changing the order anyone sees. This is the same rule `watchtower:simulate`'s keyset paging follows, for the same reason. The management page was affected too and is fixed by the same change. ([#64](https://github.com/AhmedMerza/laravel-watchtower/issues/64))

- **`never_auto_block` now holds across a fleet, not just on the node that decided the block.** The list means "automation may not touch this, an admin still may" — the right setting for an office gateway a brute-force rule would otherwise lock out. It stopped at the node boundary: a *satellite's rule* could block your gateway, push it to the master, and the master applied it, because the payload never said what had decided it. Applying the list to every incoming record would have been wrong in the other direction — it would also refuse a satellite admin's deliberate block, the one thing the list is meant to allow. So the sync payload now carries `source`, and a receiving node applies `never_auto_block` only to a block another node's automation made. `watchtower:sync` counts what it turns away as `refused by never_auto_block`, separately from `never_block`. The README caveat added in 0.4.0 is gone. ([#56](https://github.com/AhmedMerza/laravel-watchtower/issues/56))

  **Upgrading is safe one node at a time.** A satellite older than this release doesn't send the field, and a node that cannot tell what decided a block treats it as *unknown* rather than as automation — so an old satellite keeps syncing exactly as before and its admins' manual blocks keep working. Reading a missing field as "automated" would have been stricter and wrong: it would silently start refusing an old satellite's deliberate admin blocks the moment the master was upgraded, which is a new failure caused by upgrading. Protection switches on per satellite as each is upgraded.

- **A *lapsed* local block no longer turns away a live synced one.** The never-downgrade rule protects a local decision that is in force, but the lookup behind it had no expiry filter — so a block that expired an hour ago, whose row `watchtower:cleanup` had not swept yet, still refused the master's live block. The master considered the address blocked, this node did not block it, and the run reported the disagreement as "local blocks preserved", which preserved nothing. On a daily cleanup schedule the window was up to ~24 hours. `find()` and `pick()` in the same service already ignored expired rows; this guard was the one place treating a dead row as a live decision, and it now matches them. A live local manual or auto block still wins, exactly as before. The trade, recorded deliberately: applying the synced block overwrites the lapsed row, so the management page's expired list shows the incoming reason rather than the original local one. ([#74](https://github.com/AhmedMerza/laravel-watchtower/issues/74))

- **`never_block` now covers a block arriving over sync in both directions, which is what the config file has always promised.** "An incoming sync record never downgrades a local manual or auto block" was implemented twice — once on the push-received path and once in `watchtower:sync` — and the two copies had already drifted. The pull path wrote with a raw `updateOrCreate()` that never went near `BlacklistService`, so an address in a *satellite's* `WATCHTOWER_NEVER_BLOCK_IPS` got a row and a cache entry there whenever the master blocked it, while `config/watchtower.php` described that list as covering blocks "by any means — UI, auto-block, or sync". **No request was ever wrongly blocked** — `BlockedIpMiddleware` re-checks `never_block` ahead of the cache, so the row was inert — which is exactly why it went unnoticed: what it cost was a misleading row in the blocklist, a wasted cache entry, and a documented guarantee one path didn't make. Both directions now go through a single `BlacklistService::applySync()`, so the guard, the whitelist check, the event and the cache strategy are decided once; `watchtower:sync` counts what it turns away as `refused by never_block`, and still rebuilds the cache **once per run rather than once per record**, which is what a per-record write would have cost on a master's whole blocklist. ([#38](https://github.com/AhmedMerza/laravel-watchtower/issues/38))
- **The blocks a satellite pulls no longer carry the master's `log_entry_id`.** It is a ULID into *this* node's `watchtower_logs`, so the copied value named a request the satellite had never seen — a link, in the management page, to an entry that isn't there. The push direction never sent it; now neither does the pull. ([#38](https://github.com/AhmedMerza/laravel-watchtower/issues/38))

**Unchanged, and now tested on both halves:** `IpBlocked` — and with it the block webhook — still fires where a block is *received* and not where it is *replicated*, so each block is announced once, by the environment that received it, rather than again by every satellite that later pulls it. A pushed block applied on the master fires it; a block `watchtower:sync` pulls does not. Nothing to do on upgrade.

## [0.5.0] - 2026-09-21

### Added

- **A management page, so managing blocks no longer means writing JSON by hand.** Without LogScope, the only way to see or change the blocklist was the API; `/watchtower` (your route prefix) now lists what is blocked — address or range, scope, source and source environment, reason, who blocked it, when, and when it expires, 25 to a page — with a block form (IP or CIDR, a reason, and 1 hour / 24 hours / 7 days / permanent), filters by source and by active / expired / all, and an unblock that asks first. **It mounts in both modes**, not just standalone: LogScope's panel acts on one address at a time from a log entry and has no list of what is currently blocked, so a LogScope install had the same gap; there the page is at `/logscope/watchtower`, and a block carrying a `log_entry_id` links back to the entry it came from. Authorization is **the same check as the API and not a second one** — the `viewWatchtower` Gate standalone, LogScope's own check otherwise — so there is no setting that can expose the page without the API, and a failed check is still a 403 rather than a redirect to a login page. `WATCHTOWER_UI_ENABLED=false` drops the page and keeps the API. **Expired blocks are listed on purpose**, because `watchtower:cleanup` deletes those rows and after that "it expired an hour ago" and "it was never blocked" look identical. **Unblocking from the page lifts exactly the row you clicked**, which is deliberately *not* what `DELETE /api/block/{ip}` does: an address holding both an app-wide block and a scoped one is two rows under two buttons, while the API endpoint still lifts every scope, because "unblock this address" has to keep meaning the address can use the app again. The form posts a duration rather than a datetime, so the page cannot write an expiry in the past — a block that never blocks anything — while the API keeps taking an arbitrary `expires_at`, since a caller has a reason to name one. ([#18](https://github.com/AhmedMerza/laravel-watchtower/issues/18))
- **The page is server-rendered, with no build step and nothing loaded from the network.** One inline stylesheet, no JavaScript at all: no npm, no CDN, no `vendor:publish`ed assets that go stale against the PHP rendering them, and it works on a host with no outbound access. This is a deliberate break from LogScope's approach — LogScope's UI is a real application and earns its Tailwind-and-Alpine bundle, while this is a table and a form, and a firewall's management page is the worst place to depend on a third party's uptime. The unblock confirmation is a round trip rather than a `confirm()` dialog, so **nothing here needs a `script-src` exception**; a strict CSP does still need `style-src 'unsafe-inline'` for the stylesheet. Filters and the current page live in the query string, so a filtered list is a shareable link and survives a refresh. The colours follow the operating system's light or dark setting, and `vendor:publish --tag=watchtower-views` takes the templates if you want your own. ([#18](https://github.com/AhmedMerza/laravel-watchtower/issues/18))
- **Escalating block durations for repeat offenders** (`WATCHTOWER_ESCALATION`, **off by default**). A fixed hour is a pause rather than a deterrent for someone who comes back, so apps end up hand-rolling a ladder in a controller; with this on, an address that earns a *second* auto-block gets a longer one and a third longer again. The **first** auto-block always lasts `block_duration_minutes` and the new `escalation.repeat_durations` list is the 2nd, 3rd, 4th… with its last value repeating — defaults read 1 hour → 6 hours → 1 day → 1 week. Keeping the first block out of the list is deliberate: two settings claiming the same number is how they drift apart, and it means switching escalation on can lengthen a block but never shorten one. **The count decays** — an address quiet for `decay_days` (default 30) starts again at the bottom, so an address reassigned to somebody else isn't serving the last tenant's sentence, and `watchtower:cleanup` forgets those ledgers on its next run. **A `warn`-mode near miss and an address held back for being shared cost no rung**, because neither was blocked; the shared-address downgrade to a *scoped* block is a real block and does count. **Manual blocks and blocks arriving over sync are untouched** — both carry the expiry their caller asked for, and only the auto-block engine consults the ladder. Counts are kept **per address per scope**, so two offences on your login routes don't decide how long an app-wide block lasts, and an IPv6 client keeps one ledger for the whole /64 a block would cover rather than a fresh one per address it hops to. A rung of `0` or less is **dropped rather than used**: it would put `expires_at` at or before now, and an escalating ladder that silently stops blocking anyone is the worst way this could fail. The ledger is an improvement to a block and never a precondition for one, so a database that can't be read falls back to the flat duration and the address is still blocked, with the log line throttled. ([#19](https://github.com/AhmedMerza/laravel-watchtower/issues/19))

### Changed

- **A new migration adds the `ip_offences` table, so an upgrade needs `php artisan migrate`** — and if you publish migrations, re-run `php artisan vendor:publish --tag=watchtower-migrations` first. The count deliberately does **not** live on `blacklisted_ips`: `watchtower:cleanup` deletes a block row once it expires, which is exactly the moment the count becomes interesting, so a counter on that row would always read zero for the offender escalation exists to catch. Nothing else changes for an existing install — with `escalation.enabled` false, which is the default, the table stays empty and no row is ever written. **Counts are per environment**: sync carries blocks, not ledgers, so a satellite won't inherit the master's count. ([#19](https://github.com/AhmedMerza/laravel-watchtower/issues/19))

- **The queue the sync push job runs on is now its own setting, `WATCHTOWER_SYNC_QUEUE`** (`sync.queue`). It read `WATCHTOWER_NOTIFICATION_QUEUE`, the key that names where the block *webhook* goes — which is how the bug below stayed invisible for so long: one setting named a queue, and the one job reading it was not the job the name describes. A push to master is what keeps your other environments in sync rather than a notification, so it can now have its own worker. **Nothing moves on upgrade** — `sync.queue` falls back to `WATCHTOWER_NOTIFICATION_QUEUE` and then to `default`, so an app that set the notification queue, and runs a worker only for it, keeps pushing on exactly the queue it does today and needs the new variable only when it wants the two apart. Whichever you name, make sure a worker actually consumes it: a push nobody processes fails silently, and the block never leaves the environment that made it. ([#50](https://github.com/AhmedMerza/laravel-watchtower/issues/50))

### Fixed

- **`WATCHTOWER_NOTIFICATION_QUEUE` now moves the block webhook, which is the job it is named for.** The listener hard-coded `public string $queue = 'default'`, so an app that pointed the setting at, say, `notifications` and ran a worker only for that queue had every webhook queued on `default`, where nothing consumed it: no webhook was ever sent, and nothing errored to say so — the setting appeared to work and silently did nothing. The listener now reads it at dispatch time through Laravel's `viaQueue()` hook, which is what the property could never do, since a property initialiser cannot call `config()` and could only ever hold the literal it held. An install that never set the variable is unaffected. ([#50](https://github.com/AhmedMerza/laravel-watchtower/issues/50))

## [0.4.0] - 2026-09-20

### Added

- **Route-scoped blocks: block an address from your login routes without taking it off the whole app.** A block now has an optional `scope`, and a scoped block only applies on routes carrying the new `watchtower:{scope}` route middleware (`Route::middleware('watchtower:auth')->group(…)`; one route can name several, `watchtower:auth,admin`). This is the middle option the shared-IP guard created the need for: mobile carriers, offices and VPN exits put many people behind one address, so a block there was downgraded to a warning — which protected them and left the attacker among them free to carry on. A scoped block takes away the routes the evidence points at and leaves everyone else the rest of the app, with the sessions they already have. **It takes two changes and neither does anything alone:** declare the name in the new top-level `scopes` config list, *and* put the middleware on your own routes — Watchtower cannot do the second half, because only your app knows where its login routes are. **Scopes are opt-in everywhere and nothing changes for an existing install:** every rule and detector ships `'scope' => null`, meaning app-wide, exactly as before. A name the config doesn't declare is refused rather than stored, since a block scoped to `atuh` would enforce nothing while reporting itself as a block — the API answers 422, and a rule or detector blocks nothing and logs why. `php artisan watchtower:install` now lists each declared scope and whether any route actually carries it, which is the only place "the middleware isn't wired up yet" and "that name is a typo" are told apart. **Cost is unchanged off the scoped routes:** a request to a route without the middleware reads exactly the two cache keys it always did, because scoped blocks live in their own cache namespace that only the route middleware reads; a scoped route reads two more, for the one scope it names. `never_block` is checked before any scope, on the same terms as everywhere else, and a cache outage on a scoped route **fails open** the way the global middleware does — these are the routes an app can least afford to turn into a 500. ([#27](https://github.com/AhmedMerza/laravel-watchtower/issues/27))
- **The LogScope panel now says when an address is blocked in a scope but not app-wide**, instead of reporting it as unblocked. `blocked` deliberately stays false for a scoped block, so the panel reads the new `scopes` key and shows which routes it covers. ([#27](https://github.com/AhmedMerza/laravel-watchtower/issues/27))
- **A shared address that trips a *scoped* rule now gets a scoped block instead of only a warning.** This is the whole reason #27 was filed, and it is the one place scopes cause more blocking than before — reachable only when you have both armed a rule and given it a scope. **`warn` mode still only warns**, whatever its scope: a dry run has to stay a dry run, or configuring a rule to report would start blocking. `never_auto_block` is still a refusal, not a downgrade. A converted block is a real block, so it is logged as one, carrying `downgraded_to_scope`, and deliberately **without** `would_have_blocked` — that key stays the canonical filter for things that did not happen, and an operator filtering on it must not find a real block hiding among the near misses. ([#27](https://github.com/AhmedMerza/laravel-watchtower/issues/27))

- **Reject known attack tools by User-Agent, on by default.** A request whose `User-Agent` names sqlmap, Nikto, WPScan, masscan or zgrab now gets the same `block_response` an IP block would, instead of being served. All five announce themselves in their stock `User-Agent` and none has legitimate production traffic. **This is deliberately not a security boundary:** the client writes its own `User-Agent` and every one of those tools changes it with a single flag (`sqlmap --random-agent`), so what this removes is the background noise of unattended scanners running defaults — most of what actually reaches a production app — for the cost of one regex match, with no cache read and no DB read. Because it is spoofable, **a match rejects the request and never blocks the address**; that only happens once the new `bad_user_agent` detector is armed, which it is not by default. `never_block` addresses skip the check entirely, `user_agents.allow` wins over `deny` so you can name your own scanner rather than dropping a pattern (`sqlmap --user-agent="acme-security-audit"`), and `WATCHTOWER_USER_AGENT_FILTER=false` turns the whole thing off — read at boot, so the middleware isn't in the stack at all, and so toggling it needs a worker restart under Octane. Patterns are plain case-insensitive **substrings**, not regexes, compiled into one expression and reused, and a blank entry is dropped rather than compiled into an alternative that would match every request there is. **`curl`, `python-requests`, `Go-http-client`, `okhttp` and an empty `User-Agent` are deliberately let through** — real API clients, webhooks, mobile apps and uptime monitors send those, and the community "bad bot" lists that include them are why people switch this kind of filtering back off. Rejections are logged at **debug** on `log_channel`: a single scan is thousands of requests and this has no throttle, so production levels drop them and you turn the channel up while tuning. **On upgrade:** if you run any of those five tools against your own site from CI or a pentest box, add its address to `never_block` or its `User-Agent` to `user_agents.allow` first. ([#28](https://github.com/AhmedMerza/laravel-watchtower/issues/28))
- **`bad_user_agent`, a detector that escalates the filter from rejecting requests to blocking the address.** Off by default, and it only ever counts requests the filter already rejected, so it does nothing unless `user_agents` is on. It starts at **5 in 10 minutes** rather than the `1` `scanner_paths` uses: both read a client-controlled part of the request, but a path like `/.env` is one a real client never asks for by accident, while a `User-Agent` is a single header anyone can set to anything — including on someone else's behalf where proxy trust is loose. A real scan reaches 5 within seconds; one crafted header does not. It counts through the same `AutoBlockService::record()` every other detector uses, so `warn` mode, `never_block`, `never_auto_block` and the shared-IP guard all apply unchanged. ([#28](https://github.com/AhmedMerza/laravel-watchtower/issues/28))
- **Optional forward-confirmed reverse DNS for search-bot claims** (`WATCHTOWER_VERIFY_SEARCH_BOTS`, off by default). A request claiming to be Googlebot or Bingbot is checked both ways: its PTR record must sit under one of the bot's domains *and* resolve back to the same address. The forward half is the half that matters — whoever controls an address controls its PTR and can point it at `googlebot.com`; only Google can make `googlebot.com` resolve back. A verified crawler skips the deny list; one that fails is something pretending to be Google. ⚠️ **These are blocking resolver calls on the request path and PHP gives them no timeout** — the OS resolver decides how long they take, and they fail by *returning false* rather than throwing, so no `try`/`catch` bounds them. Since anyone can trigger the path with `User-Agent: Googlebot`, three things keep it from tying up the worker pool: **both outcomes are cached** (caching only successes would hand a spoofer a free lookup per request); the key is **the network a block would cover**, not the bare address, so one attacker-owned IPv6 /64 is a single cache entry rather than billions; and **`max_lookups_per_minute` (default 30) caps lookups app-wide**, trusting the claim and writing nothing while over budget. A successful verification is *two* lookups (PTR, then forward confirmation), so the guarantee is one verification per address per TTL rather than one round-trip. **A resolver outage rejects real crawlers rather than letting them through** — `gethostbyaddr()` cannot distinguish "no PTR record" from "the resolver did not answer", so that ambiguous verdict is cached for 5 minutes rather than `cache_hours`, while a definitive no keeps the full TTL. Only a *cache* outage fails open, and it is logged. Off by default, and it wants a local caching resolver in front of it. ([#28](https://github.com/AhmedMerza/laravel-watchtower/issues/28))

- **Auto-ban brute force and scanners without LogScope.** Four opt-in detectors react to Laravel's own signals as they happen, so they need no log table and act inside the request instead of on the next scheduled tick: `failed_logins` (`Illuminate\Auth\Events\Failed`, start at 10 in 5 min), `login_lockouts` (`Illuminate\Auth\Events\Lockout`, fired by the Breeze / Fortify / `ThrottlesLogins` throttle, start at 3 in 15 min), `scanner_paths` (configurable path patterns — `/.env`, `/.git/*`, `/wp-login.php`, `/xmlrpc.php`, `/phpmyadmin*` — matched against the decoded path, start at 1 in 5 min) and `response_bursts` (404/429 bursts read after the response is sent, start at 40 in 1 min). Each counts per IP in the cache and blocks through the same path a log rule does, so `never_block`, `never_auto_block` and the shared-IP guard all apply. **Every detector ships disabled**, and like rules they start in `warn` mode. A `scanner_paths` match answers the request itself rather than letting it through and blocking the next one, so a pattern that overlaps a live route never serves it — keep the list to paths nothing legitimate asks for. A request that matches nothing costs nothing: the middleware isn't added to the stack at all unless a request-reading detector is enabled. Detection **fails open** the way the blocking middleware already does, so a cache backend that is down or slow can't turn an ordinary 404 or a failed login into a 500 — detection is a layer on top of the app, never worth the app itself. Scanner patterns match case-insensitively against the decoded path, since scanners vary case to slip past naive matching. A detector's counter resets on every decision, so a detector held back in `warn` mode reports once per `count` signals rather than once per matching request — otherwise a burst would write a line per request, which is both a disk-filling handle for an unauthenticated attacker and the fastest way to drown the dry run warn mode exists for. Note that whether a detector is wired up at all is decided at boot: its `count`, `window_minutes`, `mode` and `patterns` are live, but toggling `enabled` needs a worker restart under Octane and similar runtimes. ([#23](https://github.com/AhmedMerza/laravel-watchtower/issues/23))
- **The shared-IP guard now works for detectors too, and names names.** Detectors have no log table to query, so they record the signed-in users seen on the requests they counted, and the would-have-blocked entry carries the actual `user_ids` alongside `distinct_users` — much easier to judge whether to arm a detector when you can see *who* was behind a flagged address. Nothing is recorded for traffic that matched no detector. **`failed_logins` and `login_lockouts` deliberately report no users at all:** the obvious candidate is the account the credentials were aimed at, but counting it would let an attacker working through a username list look like a busy office and stand the guard down — disarming it with exactly the attack it is in the way of. Use `never_auto_block` for known office and carrier ranges before arming those two. The guard carries the **same caveat as the log-based one, more sharply**: it counts signed-in users and can't tell real ones from accounts an attacker made, and for detectors that identity comes from the matching requests themselves — so signing in as a few throwaway accounts while probing is enough to downgrade `response_bursts` to warn-only for that address. Read it as protection against your own detector misfiring on a real shared gateway, not as a control an adversary respects; `never_block` is the one nothing overrides. ([#23](https://github.com/AhmedMerza/laravel-watchtower/issues/23))
- **Auto-block won't take out a shared address.** Mobile carriers put subscribers behind carrier-grade NAT, and offices, universities and VPN exits do the same, so errors counted per IP add up across many innocent people. Before blocking, watchtower now counts the distinct signed-in users the log saw from that address during the window; at or above `shared_ip_user_threshold` (`WATCHTOWER_SHARED_IP_USER_THRESHOLD`, default `3`) the block downgrades to a warning carrying `not_blocked_because: shared IP`. `0` switches the guard off, and a value that isn't a whole number falls back to the default with a logged warning rather than silently reading as `0`. The count covers all of the address's logged traffic, not just the rows the rule matched — the question is how many people a block would hit, not how many of them tripped it. Anonymous traffic counts for nobody, so a signed-out scanner still gets blocked. **It counts signed-in users, and cannot tell real ones from accounts an attacker made**, so where registration is open someone can authenticate a few throwaway accounts from their address to keep it out of reach; raise the threshold accordingly and read the guard as protection against your own rules misfiring, not as a control an adversary respects. ([#22](https://github.com/AhmedMerza/laravel-watchtower/issues/22))
- **`never_auto_block`**, a list of addresses and ranges (`WATCHTOWER_NEVER_AUTO_BLOCK_IPS`) that automation leaves alone but **an admin can still block by hand**. That is the difference from `never_block`, which nothing overrides: use this one for a gateway where a rule would be right about the traffic and wrong about the people behind it. Enforced in `BlacklistService::block()` against `source`, so every automated decision made on this node gets it — including the [#23](https://github.com/AhmedMerza/laravel-watchtower/issues/23) detectors — and refusals raise the new `NeverAutoBlockException` (a `NeverBlockException` subclass, so existing catches still work). **It does not survive sync:** a block another node's automation decided arrives as a synced block, not an automated one, and the sync payload doesn't say where it came from, so the receiving node can't apply its own list. `never_block` is still enforced on arrival and remains the list for an address that must survive a sync push. Tracked in [#56](https://github.com/AhmedMerza/laravel-watchtower/issues/56). ([#22](https://github.com/AhmedMerza/laravel-watchtower/issues/22))

### Changed

- **A new migration adds `scope` to `blacklisted_ips`, so an upgrade needs `php artisan migrate`.** The column is `NOT NULL DEFAULT ''` — `''` means global, which is what every existing row becomes — and the unique index moves from `(ip)` to `(ip, scope)` so one address can hold a global block and a scoped one at once. Nullable would have quietly dropped that guarantee: MySQL, Postgres and SQLite all treat NULLs as distinct in a unique index. If you publish migrations, re-run `php artisan vendor:publish --tag=watchtower-migrations` first. ⚠️ Rolling this migration back **fails while any scoped block exists**, because the old index can't hold two rows for one address; delete the scoped blocks first. That is deliberate — dropping them silently to make the rollback succeed would delete blocks without telling anyone. ([#27](https://github.com/AhmedMerza/laravel-watchtower/issues/27))
- **The block webhook payload carries `scope`** (`null` for an app-wide block). The payload enumerates its fields, so a receiver that ignores unknown keys is unaffected. ([#27](https://github.com/AhmedMerza/laravel-watchtower/issues/27))
- **`GET /api/status/{ip}` gained a `scopes` key**, and `blocked` still means *blocked app-wide* — a scoped block never turns it true. A caller that read `blocked` and acted on it would otherwise be acting on an address that can still reach everything but a handful of routes, which is how v0.3.0's status bug let LogScope's Unblock delete a whole /64. `DELETE /api/block/{ip}` still lifts every scope, since "unblock this address" has to keep meaning the address can use the app again; `?scope=auth` lifts one. ([#27](https://github.com/AhmedMerza/laravel-watchtower/issues/27))
- **Creating a block writes one cache key instead of rebuilding the whole blocklist.** `BlacklistService::block()` rebuilt the entire cache from the DB on every call, re-reading every active row each time — so a scanner storm creating hundreds of blocks triggered hundreds of full rebuilds, exactly when the app could least afford it. A single address (and an IPv6 network already at the block prefix) now costs one `put()`, which is all auto-block ever produces. A **range** still rebuilds, because it lives in the shared range list that can only be updated by reading it and writing it back, and rebuilding keeps that list authoritative; ranges are made by hand, one at a time. The fallback is unchanged: if the rebuild's DB read fails, the entry is still written directly so the middleware doesn't let a blocked address through. ([#23](https://github.com/AhmedMerza/laravel-watchtower/issues/23))
- **BREAKING: a rule with no `mode` now runs in `warn`, not `block`.** The global default (`WATCHTOWER_AUTO_BLOCK_MODE`) and the per-rule fallback both moved, and an invalid mode value now falls back to `warn` too — a typo shouldn't start blocking people. A rule is written from a guess about traffic nobody has looked at yet, and the cost of guessing wrong is locking out real users, so a new rule reports before it acts. **If you rely on auto-block actually blocking, set `WATCHTOWER_AUTO_BLOCK_MODE=block` (or add `'mode' => 'block'` per rule) when you upgrade** — otherwise matching IPs are logged and let through. Nothing changes for anyone who already set a mode explicitly. ([#22](https://github.com/AhmedMerza/laravel-watchtower/issues/22))
- **The would-have-blocked log says why.** Its message is now `Watchtower: would-have-blocked (auto-block did not block)` and the context carries `not_blocked_because` (`warn mode`, `shared IP` or `never_auto_block`) plus `distinct_users`, so an unarmed rule reads differently from one that fired and was overruled. In warn mode it also carries a `hint` naming the env var that arms it. `would_have_blocked: true` is unchanged and remains the canonical filter. Anything matching on the old message string needs updating.

## [0.3.0] - 2026-09-19

### Added

- **Block CIDR ranges.** A block can now be a range as well as a single IP (`203.0.113.0/24`, `2001:db8::/48`), stored as its network address. `POST /api/block` accepts one, and `DELETE /api/block/{ip}` and `GET /api/status/{ip}` take one in the path. For a single IP, status now also reports the range that blocks it. Ranges broader than IPv4 /16 or IPv6 /32 get a 422 unless the request sends `force=true`. The sync endpoint accepts any range, since the satellite already made that call. ([#16](https://github.com/AhmedMerza/laravel-watchtower/issues/16))
- **`never_block` accepts CIDR ranges**, and an address one covers gets through even when a blocked range covers it too. ([#16](https://github.com/AhmedMerza/laravel-watchtower/issues/16))

### Changed

- **BREAKING: blocking a single IPv6 address blocks its /64.** A client usually controls a whole /64 and can move to another address inside it at will, so blocking one address stopped nothing. The row is stored as the /64 (`2001:db8:1:2::/64`), which is also what webhooks and sync pushes now carry. Set the width with the new `ipv6_block_prefix` (`WATCHTOWER_IPV6_BLOCK_PREFIX`, 32–128); `128` restores exact-address blocking, and an explicit `/128` still blocks one address. IPv6 blocks made before this upgrade keep blocking just their address. **Upgrade the master and every satellite together:** a master on 0.2.x refuses ranges and /64s with a 422, so a new satellite's IPv6 and range blocks never reach it, and a 0.2.x satellite stores the ranges it pulls but never enforces them. ([#16](https://github.com/AhmedMerza/laravel-watchtower/issues/16))
- **The cache warms on the first lookup instead of at boot.** A request now makes two cache reads, the same as before, even though ranges add a key, and artisan commands and queue workers no longer read the cache when they boot. `BlacklistCache::warmOnBoot()` is removed.
- **LogScope's Unblock button checks the status again after unblocking** rather than assuming the IP is free, and shows the range when one is what blocks the IP.

### Fixed

- **A cache flush no longer switches blocking off under Octane.** The cache warmed only at boot, which Octane does once per worker, so after a flush every request went through unchecked until something rebuilt the cache (a block, an unblock, `watchtower:sync` or `watchtower:cleanup`) or the workers restarted.
- **An IPv6 entry in `never_block` now matches however it's written.** Entries were compared as strings, so `2001:DB8::1` didn't protect `2001:db8::1`.
- **A NUL byte in an IP no longer returns a 500.** `DELETE /api/block/{ip}` and `GET /api/status/{ip}` passed the path straight to `inet_pton()`, which throws on a NUL byte rather than returning false, so `%00` in the path crashed the request. Malformed input is now refused the same way as any other.

## [0.2.1] - 2026-09-17

### Security

- **BREAKING (standalone installs): the management API now refuses everyone outside `local` until the app says otherwise.** Without LogScope, the routes had only the `web` middleware: anyone could list the blocklist, and since any visitor who loads a page gets a CSRF token, anyone could block or unblock any IP. Access now goes through a `viewWatchtower` Gate that allows only the `local` environment by default, as Horizon and Pulse do; define it in your app to grant access. The check is always appended after `watchtower.routes.middleware`, so that list can add middleware but can't remove the check, and a refused request gets a 403 rather than a redirect. **If you protected the routes with `routes.middleware` (e.g. `['web', 'auth']`), you now also need to define the Gate**, or every request outside `local` gets a 403. Installs with LogScope are unchanged: LogScope's authorization still applies, and the Gate isn't used. **If you cache routes, run `php artisan route:cache` (or `optimize`) after upgrading:** a route cache built by an earlier version keeps serving the routes without the check. ([#17](https://github.com/AhmedMerza/laravel-watchtower/issues/17))

### Fixed

- **Blocking through the API no longer fails with a 500 for apps whose users aren't Eloquent models.** The controller read the user's email with `getAttribute()`, which Laravel's `database` auth provider's `GenericUser` doesn't have. Any logged-in user of such an app got a 500 from `POST /api/block`, and so did LogScope's Block IP button.

## [0.2.0] - 2026-09-17

### Security

- **Sync requests were signed but nothing verified the signature.** Satellites computed an HMAC and sent it; the package shipped no verification code and no master-side routes. The README instead asked adopters to hand-write two unauthenticated closures at `/guard/api/blacklist` and `/guard/api/block`, so anyone who could reach the master could block any IP — and have it propagate to every satellite on the next sync — or read the full blocklist. Watchtower now ships the master side: `GET /watchtower/sync/blocks` and `POST /watchtower/sync/block`, registered automatically when `WATCHTOWER_SYNC_SECRET` is set, outside the `web` group, behind a new `VerifySyncSignature` middleware that recomputes the signature with `hash_equals` and rejects timestamps outside a configurable window. ([#12](https://github.com/AhmedMerza/laravel-watchtower/issues/12))

### Changed

- **BREAKING: package renamed — `ahmedmerza/logscope-guard` → `ahmedmerza/watchtower`.** Reflects the strategic pivot away from "LogScope addon" toward "standalone Laravel app-edge blocker, with optional LogScope integration."
- **BREAKING: namespace renamed — `LogScopeGuard\` → `Watchtower\`.** All `use LogScopeGuard\…` imports must be updated.
- **BREAKING: service provider renamed — `LogScopeGuardServiceProvider` → `WatchtowerServiceProvider`.**
- **BREAKING: config file renamed — `config/logscope-guard.php` → `config/watchtower.php`.** Re-run `php artisan vendor:publish --tag="watchtower-config" --force` if you've published a customized version.
- **BREAKING: all env vars renamed — `GUARD_*` → `WATCHTOWER_*`.** Backward-compat aliases are in place until v1.0 — `WATCHTOWER_*` takes precedence, but if unset, the old `GUARD_*` values are still consulted. Scheduled to be removed in v1.0. The one exception is `GUARD_REDIS_CONNECTION`, which has no replacement (see the cache abstraction under Added).
- **BREAKING: artisan commands renamed — `guard:install` → `watchtower:install`, `guard:sync` → `watchtower:sync`.** Update the `guard:sync` schedule entry in your app.
- **BREAKING: cache key renamed — `logscope_guard:blacklist` → `watchtower:blacklist`,** which is now the prefix for per-IP entries rather than a single hash (see the cache abstraction under Added). On first boot under the new name, the old Redis key is ignored and the cache is rebuilt from the DB. No data loss; just a brief warm-up window. Nothing deletes the old key, so remove it by hand if you want the memory back.
- **BREAKING: HTTP routes moved — `/logscope/guard/*` → `/logscope/watchtower/*` (LogScope mode) or `/watchtower/*` (standalone mode).** Update any external callers.
- **BREAKING: sync headers renamed — `X-Guard-Signature` → `X-Watchtower-Signature`, `X-Guard-Timestamp` → `X-Watchtower-Timestamp`.** The sync paths moved too (below), so **master and satellites must be on the same version** — mixing pre/post-rename versions across envs will fail signature verification.
- **BREAKING (LogScope integration): the Block IP button needs LogScope 1.6.1 or later** (was 1.5.2). LogScope 1.5.2 through 1.6.0 include the pre-rename `logscope-guard::partials.ip-actions`, a namespace this package no longer registers, so on those versions the button doesn't render. `composer.json`'s `suggest` and the README say `>=1.6.1`, and the `prefer-lowest` CI job tests against a version where the integration exists.
- **BREAKING (sync wire protocol): the sync paths moved from `/guard/api/blacklist` and `/guard/api/block` to `/watchtower/sync/blocks` and `/watchtower/sync/block`,** off the management API and away from `WATCHTOWER_ROUTE_PREFIX` — the satellite signs the path it calls, so it can't depend on the master's prefix config. Master and satellites must be upgraded together. The signed string is unchanged in shape (`timestamp + METHOD + path + rawBody`) and now has a single implementation, `Watchtower\Support\SyncSignature`, used by both the clients and the middleware.
- **`PushBlockToMaster` no longer re-pushes a block that arrived by sync,** and the master ignores an incoming push for an IP already blocked locally by hand or by auto-block. Without both, a master whose own `WATCHTOWER_MASTER_URL` points at itself — the documented setup — would push every incoming block straight back to itself in a loop.
- **`watchtower:sync` now fails with a clear message when `WATCHTOWER_SYNC_SECRET` is unset,** and `PushBlockToMaster` logs a warning instead of sending a request the master will reject.
- **A push the master rejects now fails loudly.** The job asks for JSON and no longer follows redirects, so a validation failure comes back as a 422 and retries instead of being answered with a 302 to the master's home page whose 2xx read as success — which lost the block silently. An over-long `reason` is clipped to the 500 characters the master accepts before sending, rather than failing validation on arrival.
- **The sync secret is read identically everywhere** via `SyncSignature::secret()` — trimmed, and compared against `''` rather than tested for truthiness. Previously nothing trimmed it, so a trailing space from `.env` quoting became part of the HMAC key on one side of the fleet only.
- **BREAKING: `illuminate/*` is bounded to `^12.0|^13.0`, and CI tests both.** The constraint was an open `>=10.0`, so composer installed the package on Laravel 13 — and on any future major — even though the suite had never run there; the matrix varied PHP and `prefer-lowest`/`prefer-stable` but never the framework, so it couldn't have caught a break either. Each test job now pins a Laravel major and lets composer pick the `orchestra/testbench` that goes with it (`^10.0|^11.0`), so the matrix can't drift from what `composer.json` declares, and each end of the range gets a `prefer-lowest` run. Static analysis runs on Laravel 12 and 13 rather than on whichever major composer resolves as newest, since PHPStan's verdict on this code differs between them. The TrustProxies lookup in the service provider also dropped its `is_string()` guard, redundant in front of `is_a()` and read as always-true by PHPStan under Laravel 13's narrower `getGlobalMiddleware()` PHPDoc. ([#15](https://github.com/AhmedMerza/laravel-watchtower/issues/15))
- **Laravel 11 is no longer supported, because it can no longer be installed.** Laravel 11 is past security support, and the advisories that close `PKSA-mdq4-51ck-6kdq`, `PKSA-3r5d-mb8f-1qw9` and `PKSA-m5cs-t1y6-qpcs` were only ever fixed in 12.60/12.61.1 — no patched 11.x exists or will. Composer 2.10 refuses a release with an open advisory by default, so every stable 11.x is unreachable: an app on Laravel 11 cannot resolve the framework at all, and this package's own CI was quietly falling through to the unreleased `11.x-dev` branch on both of its Laravel 11 jobs. Supporting a version nobody can install, in a package whose job is blocking traffic, isn't a support claim worth making.
- **`minimum-stability` and `prefer-stable` are gone from `composer.json`,** which restores composer's default of `stable`. `dev` was what let the advisory-blocked resolutions above fall through to branch builds — `guzzle 7.8.x-dev` and `psr7 1.9.x-dev` were being installed on every `prefer-lowest` job for the same reason. Every CI job now installs released versions only.
- **BREAKING (subclassers only): `BlacklistCache::rebuild()` returns `bool` instead of `void`.** It reports whether the DB read succeeded, so `warmOnBoot()` can stand down when it didn't. PHP does not permit a `void` override of a `bool` method, so any subclass overriding `rebuild(): void` must update its signature. Callers that ignore the return value are unaffected.
- **Laravel 10 was never actually supported,** despite the old `>=10.0` constraint: the service provider uses the `Illuminate\Support\Facades\Schedule` facade, which only exists from Laravel 11. Laravel 10 is also past its security-support window. Surfaced by a new `prefer-lowest` CI job.
- **A blocked request now gets a bare response instead of going through `abort()`.** The middleware returns `block_response.message` with `block_response.status` directly, so the app's exception handler never sees it: blocked visitors get the message as plain text rather than the app's error page (a custom `errors/403` view, or Laravel's default), and clients that expect JSON no longer get a JSON body. `block_response.redirect` works as before.

### Added

- **Cache abstraction — Redis is no longer a hard dependency.** `BlacklistCache` now uses `Cache::store(config('watchtower.cache.store'))` instead of direct Redis facade calls. Any cache driver Laravel supports works: redis, memcached, file, database, array, dynamodb. New env var `WATCHTOWER_CACHE_STORE` (default falls back to your app's `cache.default`). Internally the cache uses per-IP keys (`{prefix}:ip:{ip}`) plus a sidecar index (`{prefix}:_index`) so `rebuild()` can clear stale entries on any driver — no `Cache::tags()` requirement (file/database stores don't support tagging). `composer.json` `require` swaps `illuminate/redis` → `illuminate/cache`. The legacy `cache.connection` key (`GUARD_REDIS_CONNECTION`) is ignored by the new code and has been removed from the config schema ([#32](https://github.com/AhmedMerza/laravel-watchtower/issues/32)); users wanting a non-default Redis connection should now configure a custom cache store in `config/cache.php` and point `WATCHTOWER_CACHE_STORE` at it. Performance: request-time is unchanged (one cache `get`); rebuilds do N+1 writes vs. the previous single HMSET, but rebuilds are rare (only on block/unblock/sync).
- **Auto-block warn-only mode** — new `watchtower.auto_block.mode` config (`block` | `warn` | `disabled`, default `block`) plus optional per-rule `mode` override. In `warn` mode, the engine matches rules and emits a structured `would_have_blocked: true` log entry on the configured `log_channel`, but does NOT actually block — operators can validate a rule against real traffic before flipping it to `block`. `disabled` skips a rule entirely (per-rule kill switch). New env var: `WATCHTOWER_AUTO_BLOCK_MODE`. Backward-compatible: configs that don't set a mode get the prior `block` behaviour.
- **Standalone routing config block (`watchtower.routes.*`).** Previously the package only knew how to mount routes under LogScope's prefix — when LogScope was absent, it still read `config('logscope.routes.prefix', 'logscope')` (a leak from a foreign config namespace, working only by virtue of the default). The standalone branch now reads `watchtower.routes.prefix` (default `'watchtower'`), `watchtower.routes.domain`, and `watchtower.routes.middleware` from the package's own config. New `WATCHTOWER_ROUTES_ENABLED` env flag lets users disable the management routes entirely.
- **`watchtower:install` detects LogScope and prints branch-specific next-steps.** Standalone users get a prominent warning that the management routes have no built-in auth until v1.0.
- **`watchtower:cleanup`** deletes expired temporary blocks from the database and rebuilds the cache. Watchtower schedules it daily; set `WATCHTOWER_CLEANUP_ENABLED=false` to run or schedule it yourself.
- **`watchtower.log_channel`** (`WATCHTOWER_LOG_CHANNEL`, default `stack`) — the channel Watchtower writes its own warnings and errors to. 0.1.0 hard-coded `stack`. Messages are now prefixed `Watchtower:` instead of `LogScope Guard:`, so update any alert that matches the old prefix.
- **`watchtower.sync.timestamp_tolerance`** (`WATCHTOWER_SYNC_TOLERANCE`, default 300 seconds) — how far a signed request's timestamp may sit from the master's clock. Bounds the window in which a captured request can be replayed.

### Documentation

- The sync section now says that the routes come up on **any** environment with a secret, satellites included, since registration is gated on the secret alone and satellites need it to sign ([#36](https://github.com/AhmedMerza/laravel-watchtower/issues/36) tracks separating the two capabilities). It also warns to keep satellite egress IPs in `WATCHTOWER_NEVER_BLOCK_IPS` on the master: the blocking middleware is global, so a blocked satellite stops syncing in both directions and `watchtower:sync` reports only `HTTP 403`.

### Fixed

- **Blocks were ignored behind a load balancer or reverse proxy.** The blocking middleware was prepended to the global stack, ahead of `TrustProxies`, so `$request->ip()` returned the proxy's address and never matched a blocked client IP. It is now inserted directly after `TrustProxies` (or an app subclass of it), still ahead of sessions, auth and routing. If `TrustProxies` isn't in the global stack, it still goes first. ([#14](https://github.com/AhmedMerza/laravel-watchtower/issues/14))
- **A cache outage no longer makes every request return 500.** If the blocklist lookup throws (Redis down, a mistyped `WATCHTOWER_CACHE_STORE`), the request is let through unchecked and the failure is logged at `error` on `watchtower.log_channel`, at most once a minute across all workers. ([#13](https://github.com/AhmedMerza/laravel-watchtower/issues/13))
- **The boot-time cache warm-up no longer fails every request, or floods the log, during an outage.** `warmOnBoot()` runs on every request. A cache outage made it throw, so every request returned 500 before the blocking middleware even ran; a DB outage made it write its own `warning` each time. A failed warm-up is now logged and stands down for a minute, which also drops the repeated doomed round-trip to the dead backend. The throttle is not atomic: requests already in flight at the onset of an outage can each log once before the window closes. ([#13](https://github.com/AhmedMerza/laravel-watchtower/issues/13))
- **An empty blocklist no longer costs a DB query on every request.** `rebuild()` left the cache key unset when no IPs were blocked, but `warmOnBoot()` reads a missing key as "needs warming" — so a site with an empty blocklist (the default state of a fresh install, or any site whose blocks have all expired) re-ran `BlacklistedIp::active()->get()` on every single request, forever. `rebuild()` now writes an empty index instead.
- **Watchtower now warns when `TrustProxies` isn't in the global middleware stack.** In that case blocking runs first and sees the direct peer address, which behind a proxy is the proxy's IP — the same silent failure as [#14](https://github.com/AhmedMerza/laravel-watchtower/issues/14). The warning goes to `watchtower.log_channel`, throttled.
- **A failed cache rebuild no longer lifts every block.** `rebuild()` deleted the cached blocklist before reading the database, so when the read failed, the cache stayed empty and every block was lifted until a later rebuild succeeded, even though the logged warning said the existing data was kept. It now reads the database first and leaves the cache untouched when that fails.
- **`watchtower:sync` no longer reports success when the cache rebuild failed.** `rebuild()` catches its own DB-read failure, but the command carried on, reported the sync and exited 0. Cron recorded a green run while the cached blocklist was wrong, and the only signal was a warning on a log channel nothing was watching. It now says what actually happened and exits non-zero, so a scheduler surfaces it. The new `watchtower:cleanup` does the same. ([#33](https://github.com/AhmedMerza/laravel-watchtower/issues/33))
- **A block or unblock now takes effect even when the cache rebuild after it fails.** The blocking middleware reads only the cache, and `BlacklistService` ignored a failed rebuild — so when the DB read timed out right after the write (most likely on a large blocklist under load, exactly when auto-block is busiest), `block()` saved the row, fired `IpBlocked`, pushed to the master and reported success while the IP went unblocked, and `unblock()` returned `true` while the IP stayed blocked, both until the next successful rebuild or up to 24h. This affected auto-block, the API and LogScope's Block IP button, and a master accepting a pushed block. `block()` now writes that IP's cache entry directly when the rebuild fails, and `unblock()` always forgets the IP's own entry. `watchtower:sync`, which writes rows without going through `block()`, had the same gap for every IP it had just pulled from master — loud since #33, but unenforced until a later run's rebuild succeeded. It now writes those entries directly too, and still exits non-zero. ([#42](https://github.com/AhmedMerza/laravel-watchtower/issues/42))
- **A database or cache failure while blocking is no longer reported as "IP is whitelisted".** `block()` refused a never-block IP with a plain `RuntimeException`, and every caller caught any `RuntimeException` as that refusal — but `QueryException` and phpredis's `RedisException` are `RuntimeException`s too. So a failed write was logged by auto-block as a whitelisted skip at `debug`, where production rarely looks; the API and LogScope's Block IP button answered 422 with the raw exception message, which for a `QueryException` includes the SQL and its bindings. The refusal is now `Watchtower\Exceptions\NeverBlockException`, which still extends `RuntimeException`, so existing `catch (\RuntimeException)` code keeps working, and the callers catch only that. A real failure now surfaces: auto-block's scheduled run fails and reports it, and both endpoints return a 500. ([#44](https://github.com/AhmedMerza/laravel-watchtower/issues/44))

### Upgrading from `logscope-guard` 0.1.0

- **There is no transitional `ahmedmerza/logscope-guard` package.** It has been removed from Packagist. To upgrade, `composer remove ahmedmerza/logscope-guard`, `composer require ahmedmerza/watchtower`, then work through the BREAKING entries under Changed.
